# Data model

The initial schema is intentionally limited to `User`, `Person`, `Record` and `Attachment`. It is implemented in [`migrations/0001_initial_schema.sql`](../migrations/0001_initial_schema.sql).

## Entities

### User

- `id`: application-generated primary key.
- `google_sub`: unique Google subject identifier; never taken from a request body.
- `email`: private backend identity information; not included in public queries.
- `display_name`, `avatar_url`: profile fields from the authenticated account.
- `role`: `user` or `admin`.
- `created_at`: UTC timestamp.

Google login is account authentication, not real-name verification.

### Person

- `id`, `platform`, `handle`, `display_name`, `avatar_url`, `profile_url`, `created_at`, `updated_at`.
- `platform` is currently constrained to `x`, while remaining an explicit column for future platform evolution.
- `handle` is stored without `@`; `(platform, handle)` is unique.
- `profile_url` points to the public profile, never to private identity data.

### Record

- `id`, `person_id`, `submitter_id`, `content`, optional `source_url`, optional `occurred_at`, `created_at`, `updated_at`, `status`.
- `status` is only `published` or `hidden`; public repositories query only `published`.
- `content` is a short user description, not a platform verdict or an AI-generated truth claim.
- `submitter_id` is an internal reference and must not be exposed on public pages.

### Attachment

- `id`, `record_id`, `r2_key`, `original_filename`, `mime_type`, `size`, `sha256`, `width`, `height`, `created_at`.
- Allowed user uploads: JPEG, PNG and WebP only. No video, audio, PDF or archive formats.
- Keys are generated by the server, e.g. `records/2026/09/<record_uuid>/<attachment_uuid>.png`; original filenames are metadata only.
- Original R2 objects are immutable product evidence assets. Resizes/thumbnails, if added, use separate objects and must not replace source bytes.
- The request validator caps a record at four attachments, each at 10 MiB. Revisit limits only with an explicit product/security decision.

## Relationships and visibility

- One Person has many Records; one Google-authenticated User may submit many Records.
- One Record may have up to four Attachments.
- Hiding a record is an administrative safety/moderation operation. It is not a truth judgment. Until an Admin Console exists, an authorized administrator can hide a row through D1 management with a parameterized update, e.g. `UPDATE records SET status = 'hidden', updated_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now') WHERE id = ?;`.
- Public repository methods select public Person fields and filter `records.status = 'published'`; they never select `users.email`.

Timestamps are UTC ISO-8601 strings. Application updates must set `updated_at` explicitly. Foreign keys and CHECK constraints enforce core invariants; URL, image signature, dimensions and ownership checks remain application responsibilities.
